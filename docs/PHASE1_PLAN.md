# Phase 1 설계·구현 기록

## 1. 기술 선택

| 영역 | 선택 | 이유 | 검토한 대안 |
|---|---|---|---|
| 언어·UI | Kotlin + Jetpack Compose (Material 3) | Android 공식 스택이라 배포·유지보수가 가장 안정적입니다. Compose Multiplatform으로 iOS·데스크톱 UI도 확장할 수 있습니다. | Flutter(언어·생태계가 별도), React Native(금융 계산 정밀도·로컬 DB 신뢰성에서 이점이 적음) |
| 계산 로직 | 순수 Kotlin `:core` 모듈 (`kotlinx-datetime`만 사용) | 화면과 분리해 단위 테스트가 가능합니다. Kotlin Multiplatform으로 옮기면 iOS·PC에서 그대로 재사용할 수 있습니다. | — |
| 저장소 | Room (SQLite) | 트랜잭션·외래키·스키마 마이그레이션을 지원해 데이터 무결성을 지키기 좋습니다. Room 2.7부터는 KMP도 지원합니다. | DataStore(관계형 데이터에 부적합), Realm |

## 2. 구현한 계산 규칙 (기획서 근거)

- **실제 잔고** = 초기 잔고 + 완료 거래 변화량. 예정·취소 거래는 반영하지 않습니다.
- **예상 잔고(D일)** = 실제 잔고 + D일까지의 예정 거래 변화량. 지난 날짜의 미처리 예정 거래도 포함합니다.
- **완료 처리**는 같은 거래 레코드의 상태만 바꿉니다(예정일 보존, 실제 처리일·실제 금액 기록). 그래서 예정과 완료가 중복 반영되지 않습니다.
- **이체**는 출금 계좌에서 빼고 입금 계좌에 더합니다. 소비에 포함하지 않고 순자산도 변하지 않습니다.
- **부채 계좌** 잔액은 음수로 저장합니다. 순자산 = 자산 평가액 − 부채이고, 카드 대금 이체는 순자산을 바꾸지 않습니다.
- **외화 계좌**는 원래 통화로 잔액을 보존합니다. 평가 환율을 입력하면 원화 평가액을 따로 계산하며, 환율이 없으면 순자산에서 제외하고 그 사실을 표시합니다.
- **예산**은 한도이고 거래와는 별개 객체입니다.
  - 예산 잔액 = 예산 − 확정 지출 (예: 400,000 − 100,000 = 300,000)
  - 예정 확보 후 잔액 = 예산 − 확정 − 예정 (예: = 250,000)
- **기간**은 `[시작, 종료)` 반열린 구간으로 계산합니다.
  - 급여 기준일은 1~31일입니다. 그 달에 없는 날짜면 말일을 씁니다(31일 → 2월 28/29일).
  - 같은 원본 거래를 두 기준 모두에서 조회합니다. 예산은 주 기준 하나로만 관리합니다.
- **기간 설정 변경**: 예산은 만들 당시의 시작·종료일을 저장하므로 설정을 바꿔도 기존 기록이 보존됩니다.
- **잔고 조정**은 차액만큼 `잔고 조정` 거래를 기록하고(메모에 "조정 전 → 후"), 그 기록이 곧 이력입니다. 수입·소비 통계에서는 제외합니다.
- **검증**:
  - 오류(저장 불가): 0 이하 금액, 같은 계좌로 이체, 통화 불일치, 보관 계좌 사용, 미래 날짜 완료 거래, 카테고리 종류 불일치.
  - 경고(확인 후 저장): 잔액 부족·음수 잔고. 부채 계좌는 경고 대상에서 제외합니다.
- **계좌 보관**은 잔액 0이고 예정 거래가 없을 때만 허용합니다. 그래서 보관이 자산 합계를 바꾸지 않습니다.
- **샘플 데이터 없음**: 최초 실행 시 기본 카테고리와 설정만 만듭니다.

## 3. ⚠️ 확인이 필요한 금융 계산 규칙 (제안 기본값으로 구현)

기획서에 정해져 있지 않아 합리적인 기본값으로 구현했습니다. 사용자에게 영향을 주는 규칙이므로 확인이 필요합니다.

1. **생활비로 사용 가능한 금액 공식** (`AvailableFundsCalculator`)
   `= 대상 계좌 실제 잔고 − 예산 확보액 − 예산 밖 예정 지출 − 대상 밖 계좌로의 예정 이체`
   - 예산 확보액
     - 카테고리 예산만 있을 때: 카테고리별 `max(예산 잔액, 예정 지출, 0)`의 합
     - 전체 생활비 예산이 있을 때: `max(전체 예산 − 기간 지출, 기간 예정 지출, 0)`. 이때 카테고리 예산은 하위 한도로만 보고 더하지 않습니다.
   - 예정 수입은 입금 전까지 반영하지 않고 참고로만 표시합니다(보수적).
   - 지난 기간에서 처리되지 않고 밀린 예정 지출은 "예산 밖 예정 지출"로 차감합니다.
2. **예산 초과 카테고리**: 초과해도 남은 예정 지출은 계속 확보 대상으로 봅니다(확보액 = 예정 지출). 초과분을 다른 예산에서 끌어오지는 않습니다.
3. **완료 거래의 기간 귀속**: 실제 처리일을 기준으로 합니다(예정일 11/30 → 실제 결제 12/1이면 12월 소비).
4. **미래 날짜 완료 거래 금지**: 미래 날짜는 '예정'으로만 등록할 수 있습니다.
5. **잔액 부족은 경고만**: 음수 잔고(마이너스 통장 등)를 허용합니다.
6. **신용카드(부채 계좌) 지출**: 결제 시점에 소비와 예산 사용으로 계산합니다. 카드 대금 납부는 이체라 소비가 아닙니다. 사용 가능 금액에서는 카드 결제 대금 이체가 예정으로 등록된 경우에만 차감합니다.
7. **통계·예산·사용 가능 금액은 원화 거래만** 집계합니다. 외화 수입·지출은 계좌 잔고에만 반영합니다.
8. **실제 보유 잔고**는 입출금·현금·저축 원화 계좌의 합입니다. 기타 자산·외화·부채는 순자산에만 포함합니다.

## 4. 아직 구현하지 않은 기능 (구조는 준비)

- 환전 거래: 모델에 `EXCHANGE` 유형과 `toAmount`가 있고 검증에서는 차단합니다. UI는 없습니다.
- 반복 거래·정기 결제, 예산 이월·기간 마감, 저축 목표 배정
- 카테고리 추가·편집 UI: 저장소 API(`saveCategory`)만 있습니다.
- 주간·일간 캘린더, 날짜별 예상 잔고, 표시 방식 선택
- 검색·고급 필터, CSV·엑셀 가져오기, 백업·복원, 영수증 첨부, 알림
- 금융기관 연동, 중복 검사, 예정 거래 자동 연결: `source`와 `linkedPlannedId` 필드를 준비해 두었습니다.
- 다크 모드는 시스템 설정을 따르는 색 체계로 구현했고, 앱 안의 수동 전환은 없습니다.

## 5. 알려진 제한

- 모든 거래를 메모리에 올려 계산합니다. 개인 사용 규모(수만 건 이하)를 가정했고, 이보다 커지면 기간별 쿼리로 최적화해야 합니다.
- 에뮬레이터가 없어 실제 기기 실행은 Robolectric으로 대신 검증했습니다. Release(R8) APK는 빌드만 확인했고 실기기에서 실행해 보지 않았습니다.
- Release APK는 디버그 키로 서명됩니다. Play 배포 전에 서명 키를 설정해야 합니다.
- Robolectric에서 큰 화면 설정일 때 다이얼로그 안의 텍스트 필드가 idle 상태가 되지 않는 테스트 환경 문제가 있습니다. 그래서 예산 다이얼로그는 기본 화면 크기에서 따로 테스트합니다(`BudgetDialogTest`).
- 앱 아이콘은 임시 벡터 아이콘입니다(`Logo/LooinLogo.png`는 아직 반영하지 않음).
